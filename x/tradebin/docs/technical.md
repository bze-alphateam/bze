# TradeBin – Technical Notes

## Order Book
- Markets are keyed by `base/quote`. Orders carry `order_type`, `amount`, `price`, and `market_id`.
- The matching engine (`engine.go`, `ProcessingEngine`) exposes three verbs taking a `types.Order`: `PlaceOrder` (match, then rest the remainder when the opposite level was emptied and the remainder is at least `CalculateMinAmount(price)`, refund it otherwise), `FillOrder` (match, always refund the remainder: immediate-or-cancel) and `CancelOrder` (remove the order and refund its amount). The message servers build the engine from the keeper (`NewProcessingEngine(k, k.bankKeeper, maxFillsPerOrder, logger)`, both dependencies are interfaces, the fill cap comes from the params) and call it inside the transaction, with the order from the transaction. Every store access and bank send is metered by the tx gas meter (no explicit `ConsumeGas` for matching), and any error returns to the message server and reverts the whole transaction; the engine has no cache context of its own (only the per-hook wrapper around the order-fill hooks stays).
- `PlaceOrder` and `FillOrder` assign the order id from the order counter (`AssignOrderId`, zero-filled to 24 digits) before matching, without saving; `SaveOrder` writes the order and its indexes only when a remainder rests. History rows are indexed `{takerOrderId}{makerOrderId}`. The matching math (`fillAggregatedOrder`, `getExecutedAmount`), settlement (`fundUsersAccounts`), dust, history, events and hooks are the audited matching code, unchanged.
- Same-owner merge (BZE-249). The owner-price index (`Tb/op/{owner}/{marketId}/{orderType}/{transformPrice(price)}/` → `OrderReference`, `store_owner_price_order.go`) points at the order an owner rests at a market, side and price; `transformPrice` normalises the price, so `1.5` and `1.500000000000000000` are one key. `SaveOrder` writes it through `IndexOwnerPriceOrder` and `RemoveOrder` deletes it; genesis init rebuilds it from `order_list` (it is derived state, not a genesis field) and `migrations/v5.MigrateOwnerPriceIndex` builds it from every resting order. `PlaceOrder` (`engine_merge.go`) looks it up before assigning an id: when found, the order takes the resting order's id (the counter is not incremented) and is matched as usual under that id (history index, executed and refund events), and `restOrder` adds a resting remainder to the existing order (amount += remainder, aggregate += remainder, same id, `CreatedAt` and price key, so the same FIFO position) and emits `OrderAmendedEvent` instead of `OrderSavedEvent`. An index entry pointing at a missing order fails the tx. `FillOrder` never rests, so it never merges; a cancel removes the merged order whole.
- Legacy duplicates. Before consensus version 5 one owner could rest several orders at one price. They stay separate orders. The index points at the lowest id of them: `IndexOwnerPriceOrder` writes when there is no entry or the order's id is lower than the indexed one (so the result does not depend on the order orders are saved or imported in), and `RemoveOrder` deletes the entry only when it points at the removed order. Removing the indexed order does not repoint the entry to another duplicate (that would need a scan of the owner's orders): the owner's next placement at that price creates a new order, or a later save of a remaining duplicate (a partial fill) indexes it again. Only owners with such pre-v8.3.0 duplicates can see this.
- Reused ids and history. History rows are keyed `{market}/{executedAt}/{takerOrderId}{makerOrderId}`. A top-up that matches carries the resting order's id as taker id, so two top-ups of one order matching the same maker in one block would share a key. This does not happen in practice: while an owner rests an order at a price, the opposite side at that price is empty (a remainder rests only after the opposite level was emptied), so a top-up has nothing to match. In other words, a top-up never matches and is always merged whole: its refund branches and its reuse of the resting order's id as taker id in history keys do not occur in practice, and indexers can rely on a top-up producing only an `OrderAmendedEvent` (`TestEngineMerge_TopUpNeverMatches` checks it after a partial fill, a fill-cap stop and a skipped resting order).
- Distinct owners per price level (BZE-250). `AggregatedOrder.owners` counts the owners resting at a market, side and price. It equals the number of owner-price index entries at that level by construction: the engine (`engine_owners.go`) adds one right before a `SaveOrder` that creates an entry (`createsOwnerPriceEntry`: the owner has none at the level) and removes one right before a `RemoveOrder` that deletes one (`removesOwnerPriceEntry`: the entry points at the removed order). So a new resting order +1, a merge or a partial fill of an indexed order 0, a full fill or cancel of an indexed order −1; pointing an entry at a lower id changes nothing. The count is applied to the aggregate the engine writes: `addOrderToAggregate` / `removeOrderFromAggregate` for rest and cancel, the in-memory opposite aggregate in the settle loop of `fillAggregatedOrder` for fills (decided right before each write, after the earlier fills of the same pass). Removing an owner from a count of 0 fails the tx instead of wrapping, and so does removing an aggregate whose amount reached zero while it still counts owners. `RecountPriceLevelOwners` (keeper) rebuilds every count from the index (for each aggregate, the resting orders of the level the index points at); genesis init calls it after rebuilding the index, and `migrations/v5.MigratePriceLevelOwners` after `MigrateOwnerPriceIndex`.
- Pre-v8.3.0 duplicates and the count. An owner may rest several orders at one price from before the upgrade; the index points at the lowest id and only that order deletes the entry. When that order leaves while another of the owner's orders still rests there, the entry is gone and the level counts one owner less than rest there: the count can only undercount, never exceed the distinct resting owners or go below 0. An undercount makes the surcharge more lenient for every owner who is genuinely new at the level. The one owner it treats differently is the owner of such a left-over order: with no entry they count as new, so a new order of theirs at that price pays the surcharge at the (lower) count and rests as a separate order with a new id and its own entry (+1). A partial fill of the left-over order creates an entry for it (+1) as well. Either way the count returns to the entries at the level.
- `fillAggregatedOrder` works in two passes. `matchPriceLevel` (`engine_match.go`) walks the opposite level with `IteratePriceOrders` (the `Tb/p/` price index in key order; ids are zero-filled, so that is FIFO) and only reads: it loads each order, computes `getExecutedAmount` and reduces the taker, maker and aggregate amounts, collecting the fills. It stops, in this order, when the taker amount is spent, when it is below the minimum amount, or when it has already examined `maxFillsPerOrder` orders and reaches another one. Every examined order counts, filled or skipped (a zero executed amount skips the order and the walk goes on). Then, with the iterator closed, each fill is settled in order (`fundUsersAccounts`, `SaveOrder` for a partial fill or `RemoveOrder`, history, `OrderExecutedEvent` and hooks) and the aggregate is written once. Nothing is written while the iterator is open, and both the orders read and the fills held in memory are bounded by the cap.
- When the cap stopped the walk, `PlaceOrder` and `FillOrder` refund the remainder with reason `max_fills_reached` (a limit order never rests while opposite orders are left at its price). A level of exactly `maxFillsPerOrder` orders is emptied without the cap stopping anything, so a limit order's remainder rests as before.
- `MsgCreateOrder` checks, in order: the price against the best opposite order on the book (`checkPriceInOrderBook`), the minimum amount, the market, the halt, then charges the price level gas, captures the maker or taker fee (decided by the opposite aggregate's existence at the price), escrows the order coins, stores the escrow dust and calls `PlaceOrder`. The escrow dust is stored before the engine runs because the engine may update the same user's dust.
- Price level gas (`msg_server_price_level_gas.go`): crowded price levels cost more gas for new makers. After the halt check and before fee capture and escrow, `MsgCreateOrder` reads the aggregate of its own side at its price; when it counts more than `priceLevelOwnersWindow` owners and the creator has no owner-price entry there, it consumes `(owners − window) × priceLevelExtraGas` on the tx gas meter (descriptor `price level spam protection`, so simulation and `--gas auto` include it; the product saturates at the uint64 maximum instead of wrapping). Running out of gas there costs only gas. The count is the one before the order matches: matching only changes the opposite side, so it is also the count of the level the remainder joins. An order that crosses the book is charged for its own side's level all the same, since its remainder may rest there. A top-up (creator already indexed at the level) pays nothing extra, and no order is refused. `MsgFillOrders` never rests, so it pays no surcharge.
- `MsgFillOrders` charges `fill_orders_extra_gas` once on entry and `fill_orders_extra_gas × index` per entry, skips entries below the minimum amount, and for each other entry builds the inverse-side order, escrows that entry's coins (settlement pays out of the module account), stores its dust and calls `FillOrder`. The taker fee is captured once, after every entry ran; a message whose entries were all skipped is refused with `ErrInvalidOrdersToFill`.
- `MsgCancelOrder` loads the order (`ErrOrderNotFound`), checks its owner (`ErrUnauthorizedOrder`) and calls `CancelOrder`.
- Messages of one block execute in tx order, so per market the book sees them in the same order the old queue (`{market}/{id}` keys) did. The module has no EndBlock.
- Maker/taker fees use params: maker fees are routed via `maker_fee_destination`, taker fees via `taker_fee_destination` (community-pool collector or burner fee collector). Create-market fees always go to the community-pool collector after optional swap to native.
- Halted markets (keeper helpers in `service_halt.go`): `MsgCreateOrder` and `MsgFillOrders` return `ErrDenomHalted` right after loading the market, before fee capture or escrow. The engine itself has no halt gate: it only runs for orders the message servers accepted.

## Liquidity Pools
- Pools are created with an initial deposit and optional `stable` flag; each pool has its own fee and fee destination.
- LP tokens follow the AMM math in `liquidity_pool.go`; slippage controls use `min_lp_tokens`, `min_base`, `min_quote`.
- `MultiSwap` walks a list of pool IDs; input/output slippage is enforced via `min_output`. `getRoutesPools` refuses a route containing a pool with a halted denom (`ErrDenomHalted`, surfaced as-is rather than wrapped in `ErrInvalidRoutes`), `validateMarketAssets` refuses new markets/pools on a halted denom, and `AddLiquidity` refuses a halted pool — all before funds move.
- Pool fees after creation (`msg_server_update_pools.go`): `MsgUpdatePools` is the only path that changes a pool, and it writes only `Fee` and `FeeDest`. Authority check, then the stateless `Validate()` (1 to `MaxUpdatesPerUpdatePoolsMsg` = 100 updates, distinct non-empty pool ids, set values), with the fee and fee split checked by `types.ValidatePoolFee` / `types.ValidatePoolFeeDestination`, the same functions `CreateLiquidityPool` calls. One loop looks up, compares and writes each entry; an unknown pool fails the message with `ErrInvalidRequest`, and gov (like x/dao) executes proposal messages in a cache context, so the writes and events of the earlier entries are discarded with it. No halt check (the halt only blocks trading). An entry equal to the stored values (compared as decimals) is skipped without a write or an event; each changed pool emits `PoolFeesUpdatedEvent`. `calculateSwapInputAndFee` and `collectSwapFee` read `pool.Fee` / `pool.FeeDest` on every swap, so the change applies from the next swap; reserves and LP supply are untouched, so LP share accounting needs nothing.
- `Keeper.swapTokens` is the single choke point of every swap (user routes, `ModuleSwapForNativeDenom`, `ModuleAddLiquidityWithNativeDenom`, the fee payer). It returns `ErrDenomHalted` for a pool holding a halted denom, which is what makes the no-swap invariant hold for every caller at once. `ModuleAddLiquidityWithNativeDenom` already treats a failed swap as "refund the coin to the caller"; the fee-payer entry points fall back to capturing the native fee as-is when the preferred fee denom's pool is halted.

## Inter-module Hooks
- `native_denom` is the target for swapping captured fees and module balances; `MsgUpdateParams` enforces it exists in bank supply.
- `min_native_liquidity_for_module_swap` must be exceeded (strictly more native reserves) in the native/pair pool before helpers like `ModuleSwapForNativeDenom`, `ModuleAddLiquidityWithNativeDenom`, or the liquidity-depth checks (`HasDeepLiquidityWithNativeDenom`, `CanSwapForNativeDenom`) will act. This prevents draining shallow pools during module-driven swaps.
- `HasLiquidityWithNativeDenom`, `HasDeepLiquidityWithNativeDenom` and `CanSwapForNativeDenom` answer `false` for a halted denom regardless of the pool depth, so the txfeecollector ante handler refuses it as a fee denom up front and the fee collector / burner classify it as non-swappable without attempting a swap (its dust takes the existing path to the black hole). Nothing changes in those modules.
- Trading fees and the create-market fee are captured via the trade module fee paths, optionally swapped to native, then forwarded to fee collector (community pool) or burner depending on configured destinations. Fees sent to `burner` are later destroyed or swapped through burner logic depending on denom type.

## Storage / Queries
- Prefixed stores keep markets, orders, pools, and user dust; gRPC/REST exposes markets, pools, order books, and params for indexers.
- Halted denoms (`store_halted_denom.go`, prefix `halted_denom/`): one key per denom with a one-byte value. `IsDenomHalted` is a single `Has()` — exact match, flat gas (`HasCost`), independent of how many denoms are halted — and `isMarketHalted` / `isPoolHalted` are two of them. The list is deliberately **not** a param: `GetParams` unmarshals the whole `Params` blob at 3 gas per byte and tradebin reads params about seven times per trade (ante, message handler, fee payer), so a few hundred 68-char ibc denoms in a param would have cost more gas per trade than the trade itself; the store makes the count irrelevant. Governance edits the store with `MsgHaltDenoms` / `MsgUnhaltDenoms` (`msg_server_halt.go`: authority check, stateless validation — valid denoms, no duplicates, at most `MaxDenomsPerHaltMsg` = 1000 per message — then the native denom refused before any write; idempotent, one `DenomHaltedEvent` / `DenomUnhaltedEvent` per denom whose state changed). Queries `HaltedDenoms` (paginated, store order) and `DenomHalted` (`query_halt.go`); genesis `halted_denoms` list imported/exported and validated (`ValidateHaltedDenoms`).

## Version History

### v8.3.0
- In-transaction order book execution: `PlaceOrder` / `FillOrder` / `CancelOrder` engine verbs called from the message servers; `QueueMessage`, the queue store (`Qm/value/`), its counter (`Qm/counter/`), the pending-cancel store (`Qm/pc/`), `queue_message_list` in genesis, the module EndBlock and param 12 (`orderBookQueueMessageScanExtraGas`, reserved) are removed. `NewOrder` split into `AssignOrderId` + `SaveOrder`. `ConsensusVersion` 4 → 5 (`migrations/v5`): every queued message is refunded once (`GetOrderCoinsWithDust` with `UserReceives`, dust stored, `OrderMessageRefundedEvent` reason `upgrade`), a queued cancel refunds nothing, then the three `Qm/` prefixes are deleted. The stored `QueueMessage` values are decoded by hand in the migration, since the proto type is gone.
- Fill cap per order: param field 11 renamed `orderBookPerBlockMessages` → `maxFillsPerOrder` (default 500, at least 1); `GetPriceOrderByPrice` (loaded a whole level into a slice) replaced by `IteratePriceOrders`; refund reason `max_fills_reached`. `migrations/v5.MigrateParams` (run by `Migrate4to5`) sets the field to its default when it is 0 and keeps any other stored value, since the field number is unchanged.
- Same-owner merge: owner-price index `Tb/op/`, a new order at a price where its owner rests an order is added to that order (same id and FIFO position), `OrderAmendedEvent`. `migrations/v5.MigrateOwnerPriceIndex` (run by `Migrate4to5`) builds the index; pre-existing duplicates stay separate and the index points at the lowest id.
- Price level owners and gas: `AggregatedOrder.owners` (field 5), params 7 and 8 renamed `orderBookExtraGasWindow` → `priceLevelOwnersWindow` (default 500) and `orderBookQueueExtraGas` → `priceLevelExtraGas` (default 25,000), both at least 1; `MsgCreateOrder` charges new owners at crowded levels. `migrations/v5.MigrateParams` sets the window to 500 whatever was stored (it counted queued messages) and keeps the extra gas (default over a 0); `migrations/v5.MigratePriceLevelOwners` writes every count from the index after it is built. Genesis init recounts the owners.
- `MsgUpdatePools` governance message (fee and fee split of existing pools only), `PoolFeesUpdatedEvent`, fee rules shared with pool creation (`types.ValidatePoolFee`, `types.ValidatePoolFeeDestination`). No store change and no migration of its own.

### v8.2.0
- Governance-halted denoms: own prefix store (`halted_denom/`, one key per denom), `MsgHaltDenoms` / `MsgUnhaltDenoms` governance messages, `HaltedDenoms` / `DenomHalted` queries, `DenomHaltedEvent` / `DenomUnhaltedEvent`, genesis `halted_denoms`, `ErrDenomHalted` (4017), halt guards in the msg servers, in `swapTokens` and in the liquidity answers; the EndBlock engine is untouched. No migration (the store is empty until a proposal writes to it), `ConsensusVersion` stays 4.

### v8.1.0
- Fee payer service (`CaptureAndSwapUserFee`) for fee capture and conversion to native denom via liquidity pools
- Queue rate limiting via `OrderBookPerBlockMessages` parameter (default 500); counter resets only when queue empties
- Pending cancel tracking: `CancelOrder` checks `HasPendingCancel` before queuing to prevent duplicates
- Min liquidity threshold now uses `MinNativeLiquidityForModuleSwap` param instead of hardcoded `50_000_000_000`
- `ModuleSwapForNativeDenom` reordered to capture coins first then swap; returns `sdk.Coin{}` on error
- `FillOrders` gas consumption uses `FillOrdersExtraGas` param (default 5,000) instead of hardcoded constant
- `IterateAllQueueMessages` handler now returns `bool` to control iteration; `RemoveQueueMessage` requires `marketId` parameter
- Queue message keys restructured to composite `{market}/{id}` format for market-scoped queries
- History order index format changed to `{messageId}{orderId}` for correct sorting
- `CalculateMinAmount` now returns error and is properly checked
- Order key precision migration (24-char/10-decimal → 32-char/18-decimal) moved to module migration (v3→v4) with write-before-delete pattern
- v2 parameters: `sdk.Coin`-based fee fields + 6 new gas/liquidity parameters
- ConsensusVersion bumped from 3 to 4
